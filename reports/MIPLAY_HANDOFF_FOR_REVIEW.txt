证伪方法：对同一帧用不同 key/IV 解密，第 3 帧结果会随 key 改变；
真正的 AES-CBC 链式下，第 3 帧的 IV 来自第 2 帧密文，与所选 key/IV 无关。
因此该脚本的帧解析或链式模型有误，KEY OK 判定为假阳性。

2. 已确定的事实（含证据来源）

2.1 两个通道 + 一条反向的媒体链路

[控制通道] 平板 --TCP 8899--> 音箱        ← 唯一被加密的通道，已破
[媒体通道] 音箱 --TCP 拨号--> 平板        ← 方向相反！音箱主动连发送端
                    ▲
                    └ 平板必须自己当 RTSP/WFD 服务器

[实测] 音箱拨入发送端，发送端在这条反向连接上推 MPEG-TS。

2.2 控制通道（TCP 8899）—— 已完全破解

  | 项 | 结论 | 等级 |
  | --- | --- | --- |
  | 算法 | AES-128-CBC，零填充 | [实测]+[反汇编] |
  | key | authKey（不是 streamKey！） | [实测]+[反汇编] |
  | IV | streamIV | [实测] |
  | IV 语义 | 跨帧自由链式（IV := 上一段密文末 16B） | [实测] |
  | 填充 | pad = 16 - (len % 16)，恒 1..16 | [实测] |
  | 完整性 | 字节反转 CRC-32，只覆盖密文（与密钥无关） | [实测] |
  | wire | '$'\|outer:u8\|cmd:u8\|seq:u16be\|bodyLen:u32be\|body<br>body = 00 07 01 e0\|flags\|pad\|crc32be\|ct | [实测] |

★ 最反直觉的一条：genAesKey(type=4) 读 SafetyKeyDeal+0x58，
而该成员由 onSessionConnect 从 authKey 字段填充 ——
所以控制通道的 AES key 是 authKey。这一条曾经让我所有解密尝试失败，
纠正后一次通过。[反汇编]（Ghidra 反编译 + 手工核对 AArch64 汇编）

密钥来源 [源码]：
java
// ProtocolSession.getKey()
System.arraycopy(UUIDGenerator.getUUID().getBytes(UTF_8), 0, b, 0, 16);
// UUIDGenerator.getUUID() = UUID.randomUUID().toString().replaceAll("-","")

→ 密码学随机，不可能从抓包推导。
但官方把它明文打印在 logcat（Cir_Miplay_UUIDGenerator: uuid:<32hex>，未脱敏）。

自校验（零填充 oracle）：
  | 场景 | 结果 |
  | --- | --- |
  | 播放期完整抓包 | ~~137/137 + 159/159 帧通过~~ 已撤回 |
  | 真机实时会话 | ~~36/40 帧通过~~ 已撤回 |
  | 错密钥对照 | ~~0/5~~ 已撤回 |

2.3 音频通道 —— 实测没有加密

[实测] 用分布检验证明（不是"看不出明文"）：

  | 数据 | 熵 | 卡方(vs 均匀, df=255) | 0xff 占比 |
  | --- | --- | --- | --- |
  | 音频原始载荷 | 7.8017 | 2,749,847 | 6.76% |
  | CTR chain 试解 | 7.9999 | 224 | 0.39% |
  | 理想均匀随机 | 8.0 | ≈255 | 0.39% |

判据：原始高度非均匀（卡方 2.75×10⁶）；而任何 AES 候选解出来都变成
教科书级均匀（卡方 224 ≈ 理论值 255）。解密把结构抹掉了 ——
若原始是密文，解密只会*保持*均匀性。→ 原始不是密文。

[反汇编] TSPacketizer::packetize 的加密是有条件的
（需 this[0x448]≠0 且 this[0x460]==1），本会话未生效；
即使生效也只 AES_CBC_encrypt_buffer 处理到 16 字节对齐处。

2.4 音频帧封装 —— 已还原并纠正

[实测] 外层是标准 RTSP 交织帧：

'$'(0x24) | 通道:u8 | 长度:u16be | 载荷

验证：对 3,095,052 字节的完整音频流按此解析
→ 3502 帧、100.00% 消费、0 次重新同步、通道恒为 0。
⚠️ 我此前（V2）记为 '$' | length:u16be，是错的。
并且 24 00 02 fc 按 3 字节 BE 读也得到 764（数值恰好对），
所以两种误读都"看起来自洽" —— 只有交织帧读法能解释"通道字节恒为 0"。

[实测] 载荷 = 12 字节私有头 + MPEG-TS：

80 a1 <seq:u16be> <unk:u16be> | de ad be ef | <subtype:u16be> | <MPEG-TS>
载荷 offset 0                    offset 8       offset 12

TS 结构 [实测]：

  | PID | 内容 |
  | --- | --- |
  | 0x0000 | PAT |
  | 0x0100 | PMT |
  | 0x1000 | PCR |
  | 0x1100 | 音频 PES（stream_id=0xC0，带 PTS） |

编码：控制通道协商为 audio/mp4a-latm（LATM/LOAS）。

4. ★ 当前唯一阻塞点：authMsgAck

4.1 现象

WFD 会话建立时有一段鉴权挑战（RTSP OPTIONS / 200 OK 的头字段）[实测]：

发送端 -> 音箱 :  authMsg:fcb9521c17e994e450fa59963d45f0e8        (16 字节)
音箱 -> 发送端 :  authMsgAck:cab7a6f7a35f9caa0ac8bd631df85319753c32e119d4adbe4ae30853efb76482   (32 字节)

反方向：
音箱 -> 发送端 :  authMsg:accae1fff32df94d2f7392aea7c63bac
发送端 -> 音箱 :  authMsgAck:2f83031802f26f551ef321431c934b1cd563b0e3e2b4b3d289ce2206ab75e437

authMsgAck 是 32 字节 = HMAC-SHA256 长度，但：

4.2 已穷尽尝试（全部失败）

* HMAC-SHA256(authMsg, key) 与 HMAC-SHA1(...)，
  key ∈ {authKey, streamKey, streamIV}（同一会话已恢复的真密钥）
* key 的 ASCII 形式与 hex 解码形式
* 正序与反序（把 authMsg 当 key、key 当 data）
* SHA256(authMsg || key)、SHA256(key || authMsg)、SHA256(authMsg||authMsg)、SHA256(key||key)
* 两个方向（发送端→音箱、音箱→发送端）的配对都试了

结果：0 命中。

4.3 给评审的关键问题

1. 这个算法可能是什么？ 已知 16 字节挑战 → 32 字节应答。
   是否可能不是 HMAC，而是：
   * 某种 TLS/DTLS 式的 PRF？
   * HMAC(key, authMsg || sessionId || deviceId) 之类的拼接了额外材料？
   * 小米自研的 safetyIntegrityData（native 里有这个导出符号）？
2. 哪里能拿到实现？ 我已有的素材：
   * libmirror-jni.so（有完整符号表，含 safetyIntegrityData(unsigned, unsigned, const uchar*, ulong)）
   * libaudiomirror-jni.so、libmilink.so 等 20 个 .so
   * libmirror-jni.so 已用 Ghidra 反编译出 9,405 个函数到 /tmp/decomp_mirror/*.c
   * 平板系统 APK 的 jadx 反编译产物（3,659 个 .java）
   建议搜索关键词：authMsgAck、authAlgorithmVal、wfd_type_encryp、
   authMsg、safetyIntegrityData
3. 能否绕过鉴权？ 例如：
   * 声明 authKeyType:0 / authAlgorithmVal:0（不鉴权）是否被音箱接受？
   * 官方发送端在未配对场景下的行为是什么？

6. 明确排除的方向（不要再走）

* ❌ 从抓包推导控制通道密钥 —— 它是 UUID.randomUUID()，不可能
* ❌ 继续爆破 KDF —— 已证伪 5,022 个候选，且密钥来源已确定
* ❌ 认为音频被加密 —— 分布检验已否定（卡方 2.75×10⁶ vs 解出后 224）
* ❌ 用 TCP 四元组派生任何密钥
* ❌ 把音频载荷里的 0x24 当重新同步标志（会脱轨）
* ❌ 尝试从外部主机（如 NAS）发起音频推流 —— 方向是反的，物理上不可能

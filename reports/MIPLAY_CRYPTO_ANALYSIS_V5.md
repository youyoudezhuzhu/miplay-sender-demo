## 0. 本轮结论（先说）

### 音频通道**没有加密**。

[实测] 音频 TCP 流的载荷是**明文 MPEG-TS / PES 封装**，不是密文。

证据是**分布检验**（比"看不出明文"强得多的判据）：

**全量统计（3,502 帧 / 2,602,864 字节的 PID 0x1100 载荷）**：

| 数据 | 熵 (bits/byte) | 卡方 (vs 均匀, df=255) | 0xff 占比 |
| --- | --- | --- | --- |
| **音频原始载荷** | **7.8017** | **2,749,847** | **6.76%** |
| CBC reset（streamKey/streamIV） | 7.9834 | 70,140 | 0.38% |
| CBC chain | 7.9833 | 70,426 | 0.38% |
| CTR reset | 7.9875 | 46,732 | 0.43% |
| **CTR chain** | **7.9999** | **224** | 0.39% |
| ECB | 7.9821 | 76,245 | 0.37% |
| 理想均匀随机（理论） | 8.0 | ≈255 | 0.39% |

> 注意最后一行：**CTR chain 的卡方 = 224，几乎正好等于均匀分布的理论值 255**
> —— 即它把一个卡方 2.75×10⁶ 的结构化数据变成了**教科书级的均匀随机**。
> 这是"输入本来就不是密文"的最强证据。

**判据的含义**：
* 原始载荷明明**高度非均匀**（0xff 占 6.76%，是均匀分布 0.39% 的 **17 倍**；
  卡方 2,749,847 远超 df=255 的临界值，均匀假设被彻底否定）→ 这是**有结构的数据**；
* 而**任何** AES 密钥/模式/偏移组合解出来的结果都变成**接近完美均匀**
  （熵 7.98+，卡方掉到 2.2×10²–7.6×10⁴，0xff 回到 0.39%）→ **解密操作把结构抹掉了**；
* 若原始是密文，解密只会**保持**均匀性，绝不可能让卡方从 2×10⁶ 降到 5×10³。
  **因此原始载荷不可能是密文。**

> 对照第 10 轮控制通道：那里的正确密钥一解，**立刻**出现可读 JSON 与连续零填充。
> 音频这里没有任何对应现象——因为它根本不需要解。

## 1. 音频帧完整格式 [实测]

```
┌─ 音频 TCP 帧（'$' 帧）────────────────────────────────────────────┐
│ 24                      frame marker                              │
│ 00 02 fc                3-byte BE length = 0x0002fc = 764         │
│ ─────────────────────────────────────────────────────────────────│
│ 80 a1                   version/type marker（固定）                │
│ 02 cd                   u16 BE = 0x02cd，**逐帧 +1**（会话内序号）  │
│ 00 14                   u16 BE = 20                                │
│ 6b 6b …                 u16，随帧变化                              │
│ de ad be ef             magic（固定，100%）                        │
│ 47 51  / 47 40 / 47 11  子类型（固定于该帧）                        │
│ <TS packets>            MPEG-TS，188 字节/包，包边界对齐到 offset 12 │
└──────────────────────────────────────────────────────────────────┘
```

**帧长**：
```
frame_size = 3 + length        （length = 3 字节 BE）
764  → 767 字节（2208 帧）
1328 → 1331 字节（673 帧）
952  → 955 字节（449 帧）
```
[实测] 对 3,095,052 字节的完整音频流，按此规则解析 **3502 帧、100.00% 字节被消费**，
无一次依赖 `0x24` 重新同步。

> **★ 关键陷阱 [实测]**：密文/载荷内部**确实存在 `0x24`**
> （实测偏移 95 / 263 / 381 / 726 都有）。因此**绝不允许**用 `0x24` 重新同步，
> 只能严格按长度推进。这一条已写入工具。

**TS 层 [实测]**：从帧内 offset 12 开始，`0x47` **每 188 字节出现一次**，
在 200/200 帧中成立 → 标准 MPEG-TS。

| PID | 内容 | 载荷性质 |
| --- | --- | --- |
| `0x0000` | PAT | 184 字节**全恒定**（明文） |
| `0x0100` | PMT | 184 字节**全恒定**（明文） |
| `0x1000` | PCR | 181 恒定 + 3 变化（明文） |
| **`0x1100`** | **PES 音频** | 184 字节**全部变化** ← 唯一的媒体数据 |

`0x1100` 包内含标准 PES 头 [实测]：

```
00 00 01 c0   PES start code + stream_id=0xc0（音频）
02 bc         PES_packet_length
84            flags（data_alignment + PTS）
81 18 21 00 51  f4 d7 8e d0   PTS
a1 32 33 3b   更多时间戳
```

## 3. 源码 / 反汇编证据（解释"为什么没有加密"）

### 3.1 控制加密的调用链不在音频路径上 [反汇编]

`TSPacketizer::setupEncrypt`（`0x3127d8` 附近）：

```c
// 取 option 0x10001c = key, 0x10001d = IV
uVar12 = (**(code**)(*plVar11 + 0x60))(plVar11, 0x10001c, &local_78);
if ((uVar12 & 1) == 0) local_78 = local_a8;      // 回退：硬编码
...
AES_init_ctx_iv(this + 0x471, key, iv);
this[0x470] = 1;
```

其中回退值 [反汇编]：
```c
local_a8  = 0x20;                                  // 长度 32
uStack_b7 = 0x0e0d0c0b0a0908;  uStack_b0 = 0xf;    // 00 01 02 ... 0f
local_c0  = 0x20;
local_bf  = 0x0706050403020100; uStack_af = 0;     // 00 01 ... 07 (+ 后续)
```
→ 缺省 key = `bytes(range(32))`（AES-256），缺省 IV = `bytes(range(16))`。

### 3.2 加密是有条件的，且该会话未满足 [反汇编]

`TSPacketizer::packetize`（`0x313bf4`）：

```c
if (this[0x448] != 0) {                 // 需要 encrypt 使能标志
  if (*(int *)(this + 0x44c) == 4) {    // 需要某种 media type == 4
     ... 检查 video/ 或 audio/ 前缀 ...
     if (*(int *)(this + 0x460) == 1) {         // ← 关键开关
        uVar17 = *(ulong *)(local_90 + 0x40) & ~0xF;     // 长度向下取整到 16
        AES_CBC_encrypt_buffer(this + 0x471, buf, uVar17);
     }
  }
}
```

即使满足条件，加密长度也**只是 buffer 长度向下取整到 16 的倍数**，
尾部不足 16 字节的部分**保持明文**。

**实测该会话中加密未生效**：全流 `0x1100` 载荷的分布是结构化的（§0 表格），
而非均匀——与"已被 AES-CBC 处理过"矛盾。

## 4. 枚举过的候选（全部失败，且失败方式一致）

规模化的 offset × mode × IV 枚举 [实测]：

* **offset**：帧内 offset 0–39 全枚举，另重点测 12 / 14 / 16 / 18 / 20（TS 边界）
* **mode**：CBC / ECB / CTR / OFB / CFB
* **IV 语义**：每帧重置为 `streamIV`；跨帧 chaining（`IV := 上段密文末 16B`）
* **key**：`streamKey`、`streamIV`、`authKey`、硬编码回退 `range(32)` / `range(16)`、
  零密钥
* **区域**：整帧、TS 载荷（184B）、PES 载荷、TS header 之后
* **评分**：熵、卡方、0xff 占比、跨帧同偏移相似度、已知 header 命中
  （`RIFF/ftyp/ADTS/OggS/Sync/000001`）

**结果**：没有任何候选产生比"原始数据"更结构化的输出；
**所有解密结果都比原始数据更接近均匀随机**。
这正是"对明文做解密"的典型signature。

## 5. 那么 8899 上拿到的 streamKey / streamIV 用在哪？

* [实测] 它们**确实是** `SET_MIRROR_KEY(0x6c)` 下发的内容，并且被
  `MirrorControl_setEncryptKey` 以 option `0x10001c/0x10001d` 注入 `TSPacketizer`；
* [实测] 但在**本次抓到的会话里**，音频 TS 流并未按加密输出
  （分布检验否定）；
* [强推断] 可能原因（未定论，不在本轮结论内）：
  * `mEnableEncrypt`（`this+0x460`）在该会话为 0；
  * 或注入发生在音频流建立**之后**，本会话未重协商；
  * 或该 option 被上层覆盖为"不加密"。

> 这一条**不影响** §0/§2 的结论：**实测数据本身不是密文**。
